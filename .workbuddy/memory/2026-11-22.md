### 绕行方案：用 api.github.com 精确重建 commit（已成功，SHA 完全一致）

思路：只要**tree + parent + 作者/提交者 + 时间戳 + 提交信息字节**完全一样，commit SHA 就一样，
拉下来的提交和远端 `dc64102` 完全等价，不产生任何分叉。

1. `GET /repos/{o}/{r}/commits/{sha}` 拿 tree sha、parent、message、author/committer。
2. `GET /repos/{o}/{r}/git/blobs/{blob_sha}` 逐个取改动文件（base64），解码后
   `git hash-object .raw` 校验是否等于原 blob sha —— 验证字节级一致。
3. `git hash-object -w` 写 blob → `git update-index --cacheinfo 100644,<sha>,<path>`
   → `git write-tree`，结果必须等于远端的 tree sha（本次一处不差：`abb91f07…`）。
4. 用 python **手搓 commit 对象**（不要用 `git commit-tree`，它会规范化消息）：
   `commit <len>\0tree …\nparent …\nauthor N <E> <epoch> <tz>\ncommitter …\n\n<msg>\n`，
   sha1 对上 `dc64102…` 后 `git hash-object -w -t commit` 写入，再 `git update-ref`。
5. 把 raw 文件直接 `cp` 覆盖工作区（不要 `git checkout`，避免 autocrlf 换行转换）。

**坑：时区**。GitHub API 统一返回 UTC `Z`，但本机 git 存的是 `+0800`，直接按 UTC 拼 SHA 对不上。
穷举 `+0800/+0000` × 消息尾部 0/1/2 个换行，只有 **`+0800` + 末尾补 1 个 `\n`** 命中
（提交信息本身不带尾换行）。以后同样操作先穷举这两维。

另外两个自伤点记一下：python 循环里 `body` 被覆盖，写文件时写成了最后一个候选；
`git hash-object -w -t commit` 前先用 hashlib 自检 sha1，能立刻发现这类错。
`refs/remotes/origin/main` 也手动指到 `dc64102`（API 确认远端 main 就是它），status 才不显示 behind。
